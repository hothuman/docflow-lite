## Что уже подготовлено

`RELEASE-MANIFEST.json` закрепляет версию, tag, target, build commit и хеши файлов. `GITHUB-DRAFT-PAYLOAD.json` — готовый локальный payload с `draft=true`, `prerelease=true`, `make_latest=false`; сам по себе файл ничего не публикует. `UPLOAD-ASSETS.txt` перечисляет файлы для загрузки. `RELEASE-NOTES.md` — текст выпуска без фиктивной ссылки на скачивание.

`CANDIDATE-CHECKS.json` — проверка контрольных сумм, состава ZIP, манифеста каждого файла Portable, соответствующих исходников, исходников зависимостей и результатов frozen-проверок. `WINDOWS-LOCAL-RECHECK.json` — отдельный повторный запуск именно CI Portable на ПК владельца: два обычных старта/закрытия, 24 Core DOCX, Service и backup/restore. Оригинальный `WINDOWS-CI-RESULTS.json` сохранён без подмены локальным протоколом.

`Site-Preview/` и его ZIP — новая внешность сайта, пока с действующей загрузкой v0.1.1. `Production-Snapshot/` — копия доступных публичных файлов и ответов сервера, не экспорт настроек Cloudflare. Прежний deployment сохраняйте в Cloudflare для полноценного отката.

## Повторная проверка кандидата

Из репозитория:

```powershell
python scripts/release_candidate.py verify --directory ПУТЬ/Release-Assets
```

При изменении одного байта внешнего файла, EXE, внутреннего файла Portable или соответствующего исходника проверка завершается ошибкой. Не обновляйте манифест, чтобы скрыть нерасследованное отличие. Если пересобираете программу, создайте новый кандидат с новым происхождением и повторите frozen-проверки.

Workflow `windows-release.yml` читает номер из pyproject.toml и поддерживает только ручную подготовку **draft prerelease** после Windows/Linux-проверок. Публикации по push нет. Существующий выпуск не перезаписывается. Этот новый путь требует проверки CI на коммите подготовки; старые успешные запуски не подтверждают новый workflow автоматически.

## Последовательность публикации после отдельного поручения

1. Проверить чистоту и актуальные состояния ветки/PR, результаты проверок и неизменность файлов кандидата. Не подменять кандидат более поздним непроверенным build. Решение о merge — отдельное.
2. Создать draft в существующем `hothuman/docflow-lite` с точными полями из payload; прикрепить файлы из `UPLOAD-ASSETS.txt`. Не публиковать повторный выпуск поверх существующего тега. Убедиться, что загрузки завершены и хеши совпадают.
3. Проверить карточку draft: **v0.3.0a6**, alpha/pre-release, target `0d4fd5e`, реальные ограничения и файлы. После разрешения владельца опубликовать предварительный выпуск. Для prerelease не использовать `releases/latest` как постоянную ссылку.
4. Только теперь собрать сайт с a6:

```powershell
python site/scripts/build_release_site.py --manifest ПУТЬ/RELEASE-MANIFEST.json --output ПУТЬ/Site-After-Publication
```

Скрипт обращается к реальному GitHub API, проверяет опубликованный prerelease, commit тега, обязательные файлы, размеры и скачанные SHA256. При 404, draft, стабильном статусе, другом commit или подмене файла новый сайт не создаётся. Нет флага обхода проверки и нет публикации из скрипта. Тесты используют только синтетические ответы; их успех не означает существование публичного a6.

5. Просмотреть новую сборку сайта локально и проверить мобильные/настольные страницы, переходы, контакты и загрузку a6. Упаковать **содержимое** каталога, а не родительскую папку. Сохранить хеш архива.
6. По разрешению загрузить сайт через **Direct Upload** в существующий Cloudflare Pages **docflow-lite**. Не создавать новый проект, не менять домен, аналитику, формы, индексацию и платежи. ZIP приложения остаётся в GitHub, не в Pages.
7. Выполнить `site/scripts/verify_public_site.py`, проверить главную, Service, условия, приватность, настоящий 404, заголовки, активный EXE ZIP, SHA256, консоль и отсутствие сбора данных. Обновить реальное состояние публикации в README/трекере. Историческая проверка 49 пунктов предыдущего сайта — только исходное состояние.

## Откат

Сайт: выбрать предыдущее проверенное production deployment в Cloudflare и подтвердить HTTPS, скачивание и страницы. Публичная файловая копия полезна для сверки; без экспорта настроек не считать её полной резервной копией аккаунта.

Приложение: распаковать прежнюю версию отдельно и открыть проект из копии, сделанной **до** обновления. Не открывать изменённую базу старой программой без подтверждения совместимости. Публичный дефектный файл не заменять молча: описать проблему, прекратить рекомендацию этой версии и подготовить новый номер/исправленный prerelease.

## Остаточные вопросы и решения владельца

- Цифровая подпись отсутствует; сертификат, издатель и последующее подписание требуют решения владельца. Для alpha это раскрыто, подпись/SmartScreen не имитируются.
- Лицензии, правообладатели и брендинг не менялись. Собственная открытая лицензия DocFlow не вводится. Перед публичной поставкой владелец подтверждает применимые условия использования оригинального продукта; агент не назначает их самостоятельно. Сторонние условия поставляются по фактическому составу.
- Юридический PR №4 остаётся draft. Исполнитель, реквизиты, окончательные условия заказа/приёмки/поддержки и обработка данных не считаются утверждёнными. Форма выключена.
- Визуальная приёмка всех DOCX в Word, проверка удобства a6 владельцем, реальные материалы КлинТек и клиентский пилот не выполнены. Эти границы явно сообщаются в alpha; пилот и перенос реальных данных не входят в публикацию.
