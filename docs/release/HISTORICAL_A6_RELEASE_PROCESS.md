# Публичный предварительный выпуск DocFlow

Текущий номер читается из pyproject.toml; согласованный этап — alpha 0.3.0a6. Владелец разрешил merge PR №5, тег, prerelease и обновление существующего Cloudflare после обязательных проверок. PR №4 не объединяется автоматически.

Условия оригинального продукта подтверждены владельцем и находятся в LICENSE.txt. Это не утверждение всех проектов услуг и обработки данных.

## Один источник поставки

Финальный BUILD-INFO должен указывать commit, который используется как target выпуска. Source ZIP соответствует этим исходникам. Локальные и CI-сборки, временные PR merge-коммиты и разные кандидаты не смешиваются.

Исторический комплект 0d4fd5e и подготовка 69578dd сохранены отдельно. Они не являются результатами будущего финального commit.

## Проверки до merge

Проверьте рабочее дерево, точный head PR, необходимые замечания, Windows/Linux и браузерный CI, затронутые сценарии, документы, источник ресурсов и лицензии. Изменения схемы — только после копии и проверки восстановления.

Проверка владельцем и Microsoft Word отмечаются отдельно. LibreOffice не называется Word. EXE имеет фактический статус подписи; отсутствие SmartScreen не обещается.

## Проверенная сборка main и draft

После разрешённого merge запустите workflow Windows portable prerelease preparation на main с prepare_draft=true. Он устанавливает lock с SHA, проверяет исходники, собирает onedir, лицензии и исходники библиотек, запускает распакованный EXE и подготавливает draft.

Перед созданием draft scripts/prepare_github_draft.py проверяет контрольные суммы, Source, лицензии и точное равенство build commit / target. Локальная подготовка payload сама не публикует Release.

Сохраните CI-артефакт в постоянной папке, сверьте его digest, оригинальные файлы и provenance. Проверьте именно итоговый Portable на доступной Windows вне checkout. Не заменяйте оригинальный CI-протокол локальным: сохраняйте их отдельно.

## Публикация приложения

Проверьте карточку draft, версию, prerelease, target, завершённые загрузки, notices и SHA. Не заменяйте существующий выпуск или файлы под прежним номером. Опубликуйте проверенный предварительный выпуск в разрешённом объёме.

Скачайте публичные файлы, проверьте SHA256 и target тега. Для alpha не используйте releases/latest как постоянный адрес: GitHub может не считать prerelease последним стабильным выпуском.

## Сайт после приложения

Создайте RELEASE-MANIFEST.json с version, tag, release_target и assets из проверки выбранных файлов. Выполните:

~~~text
python site/scripts/build_release_site.py --manifest ПУТЬ/RELEASE-MANIFEST.json --output ПУТЬ/Site-Public
~~~

Скрипт проверяет реальный опубликованный prerelease, commit тега, наличие, размеры и скачанные хеши файлов. При draft/404/другом target или подмене загрузка a6 не включается.

Просмотрите сайт локально. Загрузите содержимое каталога через Direct Upload в существующий Cloudflare Pages docflow-lite. Новый хостинг не создавайте. Формы, аналитика, платежи и индексация остаются выключенными.

Проверьте production через verify_public_site.py с ожидаемыми PDF/demo и release manifest: HTTPS, главную, Service, условия, приватность, лицензию, настоящий 404, заголовки, download/SHA и build-info. Затем выполните браузерную проверку реального сайта.

## Откат и передача

Сохраните прежний deployment Cloudflare. Для отката сайта выберите его и проверьте ответы/загрузки. Копия публичных файлов — дополнительная страховка, не экспорт настроек аккаунта.

Для отката программы используйте прежний EXE и проект из копии до обновления. Не открывайте изменённую базу старой версией без подтверждения совместимости.

Финальная папка: Portable, Source, ThirdParty Sources, LICENSE, BUILD-INFO, SHA, CI и локальные отчёты, сайт, демо, инструкции, снимки и ограничения. Истекающий CI-артефакт не должен быть единственной копией.

Официальные инструкции: [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

## Проверка активированного сайта

Браузерный CI использует site/tests/prepare_browser_release_fixture.py: настоящий путь активации с синтетическими ответами Release и 64-символьным SHA. Его site/build — только тестовая фикстура, НЕ архив размещения. Перед Direct Upload соберите настоящий сайт через build_release_site.py по проверенному PUBLIC-RELEASE-MANIFEST и выполните browser_check.cjs на копии этого результата в site/build. Preview без публичного SHA не заменяет эту проверку. После размещения выполните HTTPS/browser QA production.
